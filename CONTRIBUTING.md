# Contributing

Bug reports, reproducible test cases, documentation improvements, and focused
pull requests are welcome. Follow the [Code of Conduct](CODE_OF_CONDUCT.md).
For usage questions, see [Support](SUPPORT.md). Report vulnerabilities privately
using the [Security Policy](SECURITY.md), not a public issue or pull request.

## Before starting

Search existing issues and pull requests to avoid duplicates. Open a feature
request before investing in a substantial change, especially one affecting Elo
rules, saved data, standings, or packaging. Describe the problem and proposed
behavior, not only an implementation.

The repository does not currently declare a project license. Ask the maintainer
to clarify licensing before submitting code intended for redistribution. Do not
add or change license terms as part of an unrelated contribution.

## Development setup

Use Python 3.10 or newer with Tkinter. The source application uses the Python
standard library; PyInstaller is needed only for executable packaging. Windows
is the packaged target. Fork the repository and work on a focused branch.

Run the source application with `python -B elo_calculator.py` and the full test
suite with `python -B -m unittest -v` from the repository root. Run tests with a
working Tk display so graph and theme checks execute; disclose any skipped tests.
Do not run application smoke tests against your everyday league data. On
Windows, point `LOCALAPPDATA` at a separate test directory before launching a
test application, or use a separate test account.

## Scope and tests

Keep changes small and preserve unrelated behavior and diagnostic output. Add a
regression test for a bug fix. Check the relevant areas:

1: Elo rules, draw handling, ranking priorities, and historical replay must remain
consistent with saved match data.

2: Persistence changes must preserve supported older saves. Test migration,
validation, failed saves, and recovery; discuss schema changes in the pull request.

3: GUI changes should be checked in light and dark themes, at different window
sizes, and with keyboard navigation. Use synthetic leagues and anonymized images.

4: Graph and ranking changes should preserve point-to-match links and avoid
rescanning the entire history for each observation.

Read [the project working protocol](AGENT_PERSONAL_CUSTOMIZATION.md) before
editing. Append a record to `历史工作记录.txt` describing the change, affected
files, verification results, and actual commit/push status. Never rewrite earlier
work records.

## Pull requests

Use the pull-request template and explain the problem, solution, test commands,
results, limitations, and any save compatibility implications. Reference a
related issue when one exists. Run `git diff --check` and inspect `git status`
before committing.

Do not include credentials, personal league databases, backups, recovery files,
audit logs, local settings, generated bytecode, build caches, or vendored tool
changes. Some generated files are already tracked; leave them unchanged unless
the task explicitly concerns them. Executable and ZIP publication is a separate
maintainer-reviewed step; source changes alone do not require rebuilding a release.

Review may request changes or additional evidence. Acceptance and response times
are not guaranteed. Maintainers may close duplicate, out-of-scope, or unreproducible
submissions with an explanation.
